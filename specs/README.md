## 流转口径（2026-09-02 立归档原则，2026-09-03 扩展）

1. **收官归档**（`archive/`）：终判 ✅ 且无未决项。人工走查类待办（真机手测 / 实机验证 / 打包实测）统一**移交预生产测试清单**后即可归档，不再挡归档。
2. **审查归档**（`review-ing/`）：主体落地但存在待复核项（收尾清单、真实 LLM 对拍、真机走查）→ 复核通过移入 `archive/` 转正，发现重大缺口移回 `specs/` 复工。
3. ~~**分支实现归档**（`branch-implemented/`）：实现发生在未合并的 `next/*` 分支 → 分支合并主线后移入 `archive/` 转正~~ → **2026-09-08 调整为「分支实现参考」**：coord-chain 改为本阶段方案、不再经分支实现与合并，该目录仅保留其底层实现快照供参考，不再作为流转区使用（新 spec 不入此区）。
4. **废弃归档**（`archive/deprecated/`）：拍板废弃 / 计划失效，保留溯源，不作为任何实现或出口依据。
5. **第二阶段规划区**（`next-version/`）：主线项随 `docs/features/next-version-plan.md` A–E 推进；储备项不裁撤、不在本计划内，立项时点随各自功能域规划。开工时 `git mv` 回 `specs/<name>/` 转为活跃 spec。
6. **第三阶段规划区**（`next-next-version/`，2026-09-14 立）：承载 next-next 版本（能力宿主路线）的 spec，**建立在 next-version 之上**——不与之并行占用资源，也不改写其任何内容；next-version 全线优先。**启动前置**：地基支柱（capability-plane）先于其余三支柱；module-system B1（registry 动态化）落地后才接动态注册；域网链路（domain-network）的跨域治理批以 coord-chain OC1.5–OC4.5 安全加固完成为硬前置。开工时同样 `git mv` 回 `specs/<name>/`。
7. **延伸立项**：spec 主体收官但剩余项构成独立工作面时，剩余项移出新 spec，原 spec 收官归档（先例：sandbox → sandbox-next；cmb-adoption → cmb-next）。
8. **合并**：方向被后继方案吸收时以存续方为主，被并方文件作为工件保留在其目录内（先例：prototype-companion → design-systems-advance/prototype-companion/；pm-design-v2 → design-systems-advance/pm-design-v2-\*.md）。
9. 移动一律 `git mv`，specs 内引用同步改写；引用约定：活 spec → 归档件 `../archive/<name>/`、→ 规划区 `../next-version/<name>/` 或 `../next-next-version/<name>/`；归档件引用活 spec 按层级回溯。
