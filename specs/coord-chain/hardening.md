# Coord Chain 方案强化：确认边界、性能与 AI 上下文

> 2026-09-12 · 方案评审稿，仅文档，不代表已实现或已验证。
> 延续 [design.md](./design.md) §16–21 的 v7 边界。保留 ledger / desktop main / renderer 分层、七模块入口、工作区共享开关、节点 opt-out 和本地物化确认交互。

## 1. 先消除规范歧义

本文细化既有工作包 27–35，不新增协议运行时或产品模块。旧设计 §3–7 中“一主题一链”“创始人单签驱逐”“批准数多者胜”和 §9 的逐次共享确认仅作为历史背景，不得与 §17–20 混合实现。工作区主题仅发现候选，空间身份决定准入；区块确认不等于业务审批。

§14 的查询 <10ms、diff 毫秒级、百兆网络约 10MB/s 均为待验证目标或估算，不能作为已经达成的承诺。50 节点全互联是每节点至多 49 条对等连接、全网至多 1225 条无向连接；多空间还会放大内存、队列和校验工作量，不能只按单空间计算。

## 2. confirmed 必须先有可证明的安全边界

现有 §17.3 的“同 round 不双签”不足以保证跨 round 安全：成员可能在 round 0 为 A 投票，在 round 1 为同高度 B 投票，两边都形成 quorum。因此不能仅靠轮次递增或稳定排序把结果称为终局。

在任务 27 的协议评审中，必须交付以下状态表，再进入实现：

- **故障假设**：明确允许多少崩溃、离线和恶意签名成员；多数派仅有诚实节点和交集约束时的安全结论，不能泛称 Byzantine 安全。若要求容忍 f 个恶意 validator，须论证 validator 总数、quorum 交集和锁规则，不能仅把配置切成 twoThirds。
- **跨轮次锁与恢复**：定义 lock、证书、投票条件和解锁证据；锁及已签票必须在向网络发送前持久化。进程崩溃、重启、重复提案不得允许冲突投票。
- **成员切换**：明确唯一生效高度、旧 epoch 确认的治理证书以及新 validator set 的推导；同高度不得同时按新旧集合独立确认为合法。
- **分区可用性**：没有 quorum 时继续积累允许共享的 provisional 记录，不伪造 confirmed；重连可整理 provisional 分支，但不能通过“签名更多”覆盖已确认前缀。
- **冲突确认故障**：发现两个冲突 confirmed 证书时停止该空间的确认推进，保存证据并在现有状态/日志表面报告；不自动回滚本地文件，不以字典序掩盖协议故障。

任务 30 必须包含跨 round 冲突票、投票落盘前后崩溃、epoch 切换与网络分区的模型/性质测试。具体共识算法及容错参数仍是评审决策，本文不假定已有安全实现。

## 3. 同步与应用性能：限制工作量而不是丢事实

采用现有 main 同步服务和可重建 SQLite 视图，建议以下初始可调预算；这些是实验起点，须记录硬件与负载后校准。

| 路径 | 约束与建议初值 | 超限或失败行为 |
| --- | --- | --- |
| 控制消息与 blob | 控制消息独立排队；blob 每 peer 同时接收至多 2 块，单空间至多 4 块 | 暂停请求下一块，给确认/成员消息留带宽；不得丢已签事实 |
| 队列 | 每 peer、每空间及进程级同时限制字节数与条目数；高低水位均显式配置 | outbox 持久化，背压、退避带抖动；不无限内存排队 |
| 重放与校验 | 分批校验与事务投影；每批初始至多 128 条，达到 8ms CPU 时间片即让出事件循环 | 保留校验游标；未验证记录不得进入 confirmed 视图 |
| 视图与 IPC | 按 root + spaceId + revision 查询；初始每页 100 条，游标分页 | 批量变化合并通知，随后补拉增量；不逐记录全表重查 |
| UI 通知 | 非终态进度最多每 100ms 合并一次 | 终态、错误、权限变化立即发送；合并通知不合并账本事实 |
| 面板隐藏 | 停止该面板计时动画与重复数据拉取，保留一次失效标记 | 再显示时按 revision 补齐；节点同步生命周期不依赖面板挂载 |

同步配额必须跨空间共享调度，避免每个空间都合法却耗尽整个应用。大对象的哈希/解析和重放批次须实测主线程阻塞；若不能满足时间片预算，在既有 main 服务内部评审 worker 执行，不改变 core 或 IPC 所有权。

不以 mtime 相同代替内容完整性验证；取消下载保留已校验块，错误块不得提升为可用对象。重连/重试用 recordId、CID 和持久游标去重，策略变化后重新授权 outbox 项。

## 4. UI 流畅度与增量一致性

维持现有任务树、来源 tag 和日志入口。动画只用于已有展开、状态切换和进度反馈，不添加新弹窗或导航步骤。

- 列表按稳定 workId/recordId 保留行身份；新日志只增量追加，避免以数组索引或 confirmed 状态作为 key 导致全行重挂载和焦点丢失。
- 快照与增量共享 revision 协议：先缓冲增量，再装载快照并应用高于快照 revision 的事件；缺口触发一次补拉。旧 workspace/space 请求不能覆盖当前显示。
- 昂贵详情按当前可见或展开项读取；摘要、详情及可用性携带版本，不能把新标题与旧内容拼成看似一致的卡片。
- 高频时间戳放在小组件中刷新，避免每 100ms 重渲染整棵任务树；折叠内容不执行无用计时。
- 尊重 reduced-motion；后台/隐藏面板停止装饰动画。进度跳到终态时立即显示真实结果，不等待补完动画。
- 显示同步失败时保留最近已验证数据和已有重试入口；过期内容标明状态，不静默展示为最新。

任务 32 的验收需包含键盘焦点、滚动位置、节点选中、展开状态保持，以及隐藏恢复后仅补齐一次的调用计数。

## 5. AI 接续与 skill：共享内容是证据，不是指令权限

继续通过 desktop adapter 注入结构化上下文卡，不改变 core 会话回路或权限系统。

1. 上下文卡包含 root 对应的本地绑定、spaceId、recordId、commitCid、确认状态、分类及来源版本。成员签名只证明来源和完整性，不能提升为系统指令。
2. 共享摘要、PRD、AGENTS 内容、外部证据及派生物均按不可信任务数据处理。不得因其要求关闭安全检查、读取其他 root、执行命令或安装 skill 而直接行动；仍受当前用户授权和本地权限约束。
3. 未确认、缺 blob、证据过期或 approval.subjectVersion 不匹配时，明确标为待核实，不能注入为“已完成”“已批准”或“可执行”。区块 confirmed 不授权发布、写盘或共享分类降级。
4. 使用有界上下文预算：优先目标、约束、未完成事项、有效证据和版本引用；长轨迹按需查询。摘要截断必须保留引用和缺失标记，不得通过省略否定条件改变含义。
5. 缓存以来源版本、空间、分类/策略版本和模板版本共同失效；同标题或同 themeId 不共享上下文缓存。权限收紧后不能从旧缓存泄露正文。
6. 摘要生成失败不阻塞本地会话终态：在现有状态表面保留失败/待补齐信息；不得生成空摘要并标记接续上下文已就绪。重试须幂等，不能重复创建 work.result。

以上加入任务 34 的 adapter 提示词/skill 验收；用包含恶意指令的共享文档、失效审批、缺失对象和过期摘要作测试数据，只验证其不能改变授权边界，不新增逐动作确认流程。

| 32 | revision 增量投影、可见性调度 | 快照竞态、乱序增量、焦点/滚动保持回归；隐藏前后回调与 IPC 计数 |

| 35 | 规模与长期恢复 | 5/20/50 节点及多空间、10万条记录/大文件负载下的原始测量与恢复报告 |

性能报告同时记录：冷启动与空闲基线、同步期间 p50/p95/p99 主事件循环延迟、UI 提交耗时/长任务、输入响应、IPC 字节数、CPU/RSS、磁盘和队列峰值。对比必须使用相同设备、数据、窗口可见状态和采样时长，不能把网络等待减少等同于 UI 渲染提速。

建议评审顺序：先确认安全性与规范优先级，再确定预算和失败行为，最后评审提示词及 UI 验收。此次仅完成方案细化；所有性能目标、协议性质和验收测试均仍待实现阶段验证。
